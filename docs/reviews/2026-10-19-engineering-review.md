## [high] Every Rotation change restarts the reminder cycle at quote #1, so later quotes are rarely or never shown (notifications and widget)

- **id:** `system-design-rotation-restarts-on-every-change`
- **where:** `Packages/QuotedKit/Sources/QuotedCore/Reminders/ReminderSettings.swift:157`
- **evidence:** RotationState.updated(with:) returns `RotationState(quoteIDs:, anchor: now, seed: new)` whenever the ID list changes (ReminderSettings.swift:157-159). ReminderStore.performReplan applies it on every replan (ReminderStore.swift:236-241). ReminderPlanner.plan sets base = ordinal(of: firstSlot, anchor) (ReminderPlanner.swift:55), which is 0 straight after a reset, so the next slot is always ids[0]. The widget's 'now' entry also falls back to ordinal 0 (ReminderPlanner.swift:117-118). New quotes default to 'Include in reminders' = true (AddEditQuoteView.swift:252), and saving a shared quote adds it to reminders (SharedInboxView.swift:58), so ordinary use changes the ID list often. Remove-with-Undo and reorders reset it too. I compiled QuotedCore with a driver in the scratchpad: 10 quotes, 3 a day, one new quote every 2 days, 30 days. Q1 to Q6 were each delivered 15 times. Q7 to Q24 were never delivered.
- **scenario:** A user has 10 quotes in reminders (3 a day, in order) and saves a new quote every couple of days with the default toggle on. Each save restarts the cycle at the first quote, so notifications and the widget repeat the first 6 quotes forever. The quotes at the end of the list, including every new one, never appear. This breaks F4 ('cycle through the Rotation') and F5.
- **fix:** Keep the cycle's progress across membership changes. In Packages/QuotedKit/Sources/QuotedCore/Reminders/ReminderSettings.swift, add `startIndex: Int` to RotationState with a custom init(from:) that uses decodeIfPresent and defaults to 0, so existing App Group and widget-snapshot JSON still decodes. Change updated(with:at:seed:) to take the old state's last delivered quote: ReminderPlanner.currentQuoteID(rotation: old, settings:, at: now), used only if at least one slot has passed since the old anchor, otherwise the quote the old state would play next. Map it to its index in the new list (or, if it was removed, its old index clamped to the new count), and set startIndex = index + 1 with anchor = now. In ReminderPlanner.swift, make QuoteMapper use (ordinal + startIndex) mod count, before the shuffle permutation. Update the call in ReminderStore.performReplan to pass settings. Add QuotedCoreTests showing that appending a quote mid-cycle continues with the next quote, and that a 10-quote rotation with periodic appends reaches every quote.

## [medium] Library, inbox and friendships fetches have no pagination and are silently cut at PostgREST max_rows=1000; Rotation writes are O(N) and put every ID in the URL

- **id:** `system-design-unbounded-fetch-max-rows`
- **where:** `Packages/QuotedKit/Sources/QuotedKit/Services/QuotesRepository.swift:10`
- **evidence:** fetchMine (QuotesRepository.swift:10-21), inbox() (SocialRepository.swift:262-272) and friendships() (SocialRepository.swift:92-103) have no range or limit. supabase/config.toml:18 sets max_rows = 1000, which is also the hosted default. LibraryStore.refresh replaces the whole local copy with the result (LibraryStore.swift:106), and search, reminders and the cache read only that copy. setRotation selects `id in (<every rotation id>)` and then upserts every rotation row, body included (QuotesRepository.swift:81-93). LibraryStore.addToReminders/removeFromReminders send the full current list (LibraryStore.swift:219-232). nextReminderPosition uses the local maximum (LibraryStore.swift:331-333). The design promises 'at most a few thousand rows' (docs/system-design.md:112) and 'Revisit past about 5k quotes' (docs/system-design.md:167).
- **scenario:** A user with 1,200 quotes gets only the newest 1,000. The oldest 200 drop out of the Library, Search and the cache with no error. Any of them in reminders stop appearing in notifications and the widget. The next add or reorder renumbers only the visible reminder quotes from 0, so the hidden ones keep their old positions and collide. Each single toggle also re-sends every reminder ID in the GET URL and re-uploads every body. With a few hundred reminder quotes, that means a very long query string and up to ~1 MB of upload per tap. Received shares cannot be deleted, so the inbox keeps growing and hits the same cap.
- **fix:** Packages/QuotedKit/Sources/QuotedKit/Services/QuotesRepository.swift: replace the select+upsert in setRotation with a SECURITY INVOKER RPC in a new migration, e.g. public.set_rotation(ordered uuid[], removed uuid[]). It runs one UPDATE ... FROM unnest(ordered) WITH ORDINALITY on the caller's own rows, nulls `removed`, and returns the updated rows. The arrays travel in the POST body, so there is no URL growth, no bodies and no prior select. Grant execute to authenticated and add pgTAP tests. Also compute the next position server-side. In fetchMine, inbox() and friendships(), page with .range(from:to:) in a loop until a short page comes back (or keyset on created_at,id), so results are never cut at max_rows.

## [medium] Pending deletes and shares are committed on background without a background-task assertion, so suspension can drop them silently

- **id:** `system-design-background-flush-not-protected`
- **where:** `App/AppModel.swift:142`
- **evidence:** sceneDidEnterBackground awaits toasts.flushPending(), which runs the deferred commit: backend.quotes.delete, or backend.social.share for a share (AppModel.swift:142-148, Toast.swift flushPending). The code has no UIApplication.beginBackgroundTask or performExpiringActivity anywhere (grep finds none). The docs say the commit runs 'when the app backgrounds' (docs/app-architecture.md:287). Only a kill inside the 5 s window is an accepted loss (app-architecture.md:403). POST and DELETE get no SDK retry.
- **scenario:** A user taps Send to Maya, sees 'Sent to Maya' and goes to the Home Screen within 5 s. The flush starts the POST, then iOS suspends the app a moment later on a slow cellular link, before the token refresh and insert finish. If iOS later reclaims the app, the share is never sent and nobody is told. If the app survives, the request fails on resume and a 'Couldn't send' toast shows up out of context. The same applies to a quote delete: the quote comes back on the next refresh.
- **fix:** App/AppModel.swift sceneDidEnterBackground (and ideally ToastCenter.flushPending in App/Design/Components/Toast.swift): take `let id = UIApplication.shared.beginBackgroundTask(withName: "FlushPending") { ... }` before `await toasts.flushPending()` and call endBackgroundTask(id) after it, including from the expiration handler. For shares, also persist the pending send (recipient IDs, quote snapshot, note) to the App Group before the commit and retry it on next launch if it never confirmed.

## [medium] URLSession.shared's disk cache keeps auth tokens and library/inbox responses, and nothing clears it on sign-out or account deletion

- **id:** `security-urlcache-persists-tokens-and-library`
- **where:** `Packages/QuotedKit/Sources/QuotedKit/Backend.swift:50`
- **evidence:** Backend.init defaults `urlSession: URLSession = .shared` (Backend.swift:50) and passes it to the SDK as `global: .init(headers: headers, session: urlSession)` (:65). Auth, PostgREST and Functions all go through it. Nothing in App/ or QuotedKit uses URLCache, `.ephemeral`, `requestCachePolicy` or `removeAllCachedResponses`. SessionStore.endSession (App/Stores/SessionStore.swift:369-391) wipes only the App Group, prefs and notifications. I copied the simulator's Library/Caches/com.hwei.quoted/Cache.db and inspected the copy. It holds entry 1 `POST /auth/v1/signup`, whose 2,112-byte body contains `access_token`, `refresh_token` and `email`. It also holds GET responses for /rest/v1/quotes (the full library select), /rest/v1/shares (the inbox with body/note), /rest/v1/friendships with embedded profiles, and /rest/v1/starter_quotes (stored in fsCachedData). The bundled privacy.md:44 says "Signing out removes the cached library, widget data and scheduled reminders from your device."
- **scenario:** A user signs in (the /token password or PKCE response is cached the same way the signup response was), then signs out or deletes their account. The privacy policy's sign-out promise and the 'permanently delete' promise are both false for on-device data.
- **fix:** In Packages/QuotedKit/Sources/QuotedKit/Backend.swift, replace the `.shared` default with a dedicated session, e.g. `let cfg = URLSessionConfiguration.ephemeral` (or `.default` with `cfg.urlCache = nil; cfg.requestCachePolicy = .reloadIgnoringLocalCacheData`), and pass `URLSession(configuration: cfg)`. Keep the injection point for tests. In App/Stores/SessionStore.swift endSession and once at launch, call `URLCache.shared.removeAllCachedResponses()` to purge caches written by earlier builds and TestFlight installs.

## [medium] body_format on quotes and shares has no byte limit: a 20 MB row is accepted, so any user can fill the database and a friend can bloat every inbox fetch

- **id:** `security-body-format-unbounded`
- **where:** `supabase/migrations/20261019040000_core_schema.sql:129`
- **evidence:** The only checks are `jsonb_typeof(body_format) = 'array' and jsonb_array_length(body_format) <= 200` (core_schema.sql:52-54 for quotes, :129-131 for shares). The element shape and size are not checked, and there is no per-user quota. I ran a probe as `authenticated` in a rolled-back transaction on the local stack. `insert into quotes (body, body_format) select 'x', jsonb_agg(jsonb_build_object('junk', repeat(md5(g::text),3200)))` over 200 rows was accepted (pg_column_size 20 MB). The same payload as a share to a friend was accepted too (`length(body_format::text)` = 20,482,800). The inbox select includes body_format (cached request key `/rest/v1/shares?select=...body,body_format,...`). LossyRuns drops the junk only after the whole response has been downloaded and parsed.
- **scenario:** (1) Storage DoS: a scripted account inserts about 25 quotes of 20 MB each and fills a 500 MB hosted database. The project goes read-only and the app breaks for every user. (2) A malicious accepted friend sends a few multi-MB shares. Every inbox refresh, including the background refresh, downloads and JSON-parses tens of MB on cellular, with memory spikes and slow loads, until the victim notices and blocks.
- **fix:** New migration: add `check (pg_column_size(body_format) <= 16384)` (or an immutable private.valid_runs(jsonb) that allows only objects with integer start/length and boolean bold/italic/underline) to quotes, shares and starter_quotes. Add pgTAP cases in supabase/tests/database/01 and 03 that oversized and malformed formats are rejected. Optionally add a per-user row cap trigger on quotes and shares, and a `.limit()` on the inbox query.

## [low] Optimistic rollbacks restore whole-state snapshots, clobbering concurrent mutations (reminders and friend requests end in states the server never had)

- **id:** `swift-correctness-3`
- **where:** `App/Stores/LibraryStore.swift:348`
- **evidence:** writeRotation captures `before` (line 348) after any earlier queued write's optimistic change has already been applied. On failure (lines 362-366) it restores every quote's position from that snapshot. SocialStore uses the same pattern with tuples of whole arrays: accept (SocialStore.swift:192 snapshot, :200 restore), block (:230/:245) and removeConnection (:400/:408). Each restores arrays that may already contain other in-flight operations' optimistic edits, or lack them.
- **scenario:** Offline, the user taps "Add to reminders" on quote A, then on quote B. W1 (A) fails, rolls back to the state before A and awaits refresh(), which also fails offline. W2 (B) then fails and restores its snapshot, which still contains A at the end of the reminders. Both showed error toasts, yet A is now shown in reminders, and replan() schedules notifications and the widget for A, although the server never stored it. A later refresh removes it silently. In SocialStore, accepting two incoming requests offline makes r1's failure restore S0 and then r2's failure restore S1, so r1 is shown as a friend while the server still has it pending. Sharing to that person then fails with "You can only share with friends." Online, a failed accept of r1 restores r2 to incoming after r2's decline already succeeded.
- **fix:** Roll back only what the failed operation changed. LibraryStore.writeRotation: on failure, skip the snapshot restore and rely on the existing `await refresh()` (or restore only the IDs in `ordered`/`removing` whose current position still equals what this write applied). SocialStore.accept and removeConnection: on failure, remove the optimistic friend entry by `request.id` and re-insert the original Connection into its source array by ID instead of assigning the snapshot. block: re-insert only the rows filtered for that profile and remove it from blockedProfiles.

## Rejected by verifiers

- `system-design-debug-builds-pollute-prod-analytics` (system-design): Debug builds run against the production project and log web_search_tap events into the metric that decides the roadmap. The facts are right. The Quoted scheme runs Debug (project.yml:106-107), Debug.xcconfig includes Hosted.xcconfig, and logWebSearchTap is gated only by sideEffects. That makes the claimed harm (a skewed build-or-not decision) speculative and easily avoided. It is analytics hygiene, not a defect.
- `security-profile-enumeration-request-spam` (security): Every profile is readable in bulk, and friend requests can be sent and re-sent without limit, even straight after a decline. The behaviour is by design and disclosed. system-design.md:76 states profiles are 'select: any authenticated user, since usernames are public handles', and privacy.md:35 tells users 'Your username and display name are visible to other signed-in Quoted users.' Re-requesting after a decline (a DELETE) is standard social-app behaviour. The user can block from the request row's context menu (FriendsView.swift:161), and is_blocked_pair then stops further requests, which meets the 1.2 block requirement.
