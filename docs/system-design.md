# Quoted: system design (MVP)

Status: approved for MVP build, 2026-10-18. Owner: hwei. Inputs: the founder brief, the search council decision (`docs/decisions/2026-10-18-in-app-search-council.md`), the UI critique decision (`docs/decisions/2026-10-18-ui-direction.md`) and the anonymous accounts decision (`docs/decisions/2026-10-20-anonymous-accounts.md`).

## 1. Requirements

### Functional
| # | Requirement | MVP behaviour |
|---|---|---|
| F1 | Accounts | No sign-in screens (docs/decisions/2026-10-20-anonymous-accounts.md). With no stored session the app creates an anonymous Supabase Auth account for this iPhone (`signInAnonymously`), then asks for a username (handle). Sign out is offered only with `AccountMode.emailPassword` to an account that is not anonymous, so this build has none, not even for a leftover or DEBUG email session. In-app account deletion (App Store 5.1.1(v)), after which the app starts a new, empty account. Email and password sign-up and sign-in stay in the code, switched off (`AccountMode.current` in `App/Stores/SessionStore.swift`). |
| F2 | Quotes | Create, edit and delete quotes: text, author, source. Rich text supports **bold**, *italic* and <u>underline</u>. |
| F3 | Rotation | An ordered subset of the user's own quotes (the "playlist"). The user can reorder it and switch between in-order and shuffle. |
| F4 | Reminders | Local notifications cycle through the Rotation, N times a day, spaced evenly inside a time window on chosen weekdays. |
| F5 | Widgets | Home-screen widgets (small and medium) and a Lock Screen rectangular widget show the current Rotation quote, matching the latest reminder. |
| F6 | Friends | Add a friend by exact username (sends a request), accept or decline, unfriend, block. |
| F7 | Sharing | Send a quote to one or more friends with an optional note. The recipient sees it under "Shared with you" and can save it to their library, report it or block the sender. Plain-text sharing to any app goes through the system share sheet. |
| F8 | Search | A `.searchable` bar over the library and shared quotes. The last row reads "Search the web for '<term>' quotes" and opens Google in an in-app browser (`SFSafariViewController`; this counts as unrestricted web access for the age rating, see docs/decisions/2026-10-19-web-search-browser.md). A `PasteButton` in Add brings a copied quote back. Taps on the web row are logged. |
| F9 | Starter pack | About 60 public-domain quotes with checked attributions. During onboarding the user picks some; they are copied into the library and the Rotation. |
| F10 | Favorites and profiles | Heart any of your quotes (detail and full-screen toolbars, Library swipe and context menu; Library can show only favorites). Your profile (Account > Your profile) lists your favorites and has "Show favorites to friends", off by default. A friend's profile (from Friends) shows their favorites, newest first, only when they turned that on, with Save to copy one into your library. Reminders and every other quote stay private. |

### Non-functional
- **Native and smooth.** SwiftUI on iOS 26+, 60/120 fps scrolling, no spinners on launch. The library loads from a local cache and then refreshes.
- **Secure by default.** RLS on every exposed table. The client holds only the publishable key. Server state is never trusted from the client.
- **Cheap.** $0 at MVP scale (Supabase free tier, no paid APIs, no push server).
- **App Store ready.** Privacy manifest, account deletion, UGC report and block (1.2), export compliance, app icon, versioning.

### Constraints
- A solo founder. Ship the MVP fast and keep the moving parts few.
- Supabase project `yyajndbishiyugtbpzmk`, with a publishable key in the client.
- No Google search API is available: Custom Search JSON API is closed to new customers and ends 2027-01-01.

### Data flow, main paths
1. **Launch.** Restore the session from the Keychain. With none (a fresh install, right after deleting the account, or after a lost session, section 4), show Welcome; Get started creates an anonymous account with `auth.signInAnonymously()` and shows Choose a username, and a failure (offline, or anonymous sign-ins off on the server) shows inline under Get started. With a session, render the library from the App Group cache, then refresh it from Postgres. Plan reminders and write the widget snapshot, then reload widget timelines. A launch step that fails before the session is ready (no cached profile, or the empty-library check without the onboarding flag) shows the error on the launch screen with Try again, and the app retries by itself: after 3, 10 and then every 30 seconds while the screen shows, and at once when it returns to the foreground. DEBUG builds print the diagnostic and the Supabase URL under the button.
2. **Save a quote.** Validate on the client. `insert` returns the row and updates the cache. If it is in the Rotation, re-plan reminders and the widget.
3. **Reminder fires.** iOS delivers the local notification and no code runs. A tap deep-links to `quoted://quote/<id>`.
4. **Share.** `insert into shares` with a content snapshot. RLS checks for an accepted friendship. The recipient sees it on the next refresh (on foreground and pull to refresh).
5. **Delete account.** Call `functions.invoke("delete-account")`. The function verifies the JWT and calls `auth.admin.deleteUser`, and FK cascades remove the user's rows (reports are kept for moderation with the user's id set to null; events never carry a user id). The client then signs out, wipes the cache and snapshot, and removes pending notifications. With anonymous accounts it then creates a new, empty account and shows Choose a username.

## 3. Data model (Postgres, `public` schema)

`profiles.id` and `quotes.owner_id` reference `auth.users(id) on delete cascade`. The social tables (`friendships`, `blocks`, `shares`) reference `profiles(id) on delete cascade` instead. This lets PostgREST embed the other party's profile (`sender:profiles!shares_sender_id_fkey(username, display_name)`) in one request, and deleting an auth user still cascades through `profiles`. `reports` also references `profiles`, but `on delete set null`, so a report outlives the deletion of either account (moderation evidence). `events` has no user column at all. Every table has RLS enabled and explicit grants to `authenticated` only (nothing to `anon`). Policies use `(select auth.uid())`, which is evaluated once per statement.

Anonymous accounts are ordinary Auth users. Their JWT has the role `authenticated` and the claim `is_anonymous: true`. The policies deliberately don't look at that claim, so an anonymous user has exactly the access an email user has: their own rows, their friends and the shares between them. `supabase/tests/database/10_anonymous_user.test.sql` proves the parity. The `anon` role (the publishable key with no session) still gets nothing.

The server owns every timestamp: BEFORE INSERT triggers (`<table>_stamp_created_at`) set `created_at` to the server clock whatever the client sends, `profiles` and `quotes` keep `created_at` on update (`<table>_keep_created_at`), and the other timestamps are noted per table below. Text the app trims must contain something other than whitespace on the server too (`<table>_<column>_not_blank` checks through `private.is_blank`, which strips exactly Unicode White_Space, the set Swift trims, so the server is never stricter than the app).

Implemented in `supabase/migrations/20261019040000_core_schema.sql` (plus `20261019050000_report_snapshot.sql` for the report snapshot, `20261019060000_hardening.sql` for the format, text and timestamp checks, anonymous events and report retention, and `20261021090000_abuse_limits_privacy_cleanup.sql` for profile privacy, write limits, immutable and reserved usernames, block privacy, activity and the purge of abandoned anonymous accounts) and covered by `supabase/tests/database/*.test.sql`. Foreign keys are named `<table>_<column>_fkey` (for example `shares_sender_id_fkey`, `shares_recipient_id_fkey`, `friendships_requester_id_fkey`, `friendships_addressee_id_fkey`), so embedding hints are stable.

`private` schema (not exposed by the Data API): `is_blocked_pair(a, b)` is SECURITY DEFINER with `search_path = ''`, executable by `authenticated` only, and answers only for pairs that include the caller (otherwise false), so it cannot probe other people's blocks. The trigger functions (`set_updated_at`, `stamp_created_at`, `keep_created_at`, `events_stamp_created_at`, `shares_stamp_seen_saved`, `friendships_set_responded_at`, `blocks_after_insert`, `reports_snapshot_share`) also live there and are not executable by clients. The CHECK validators `is_blank(text)` and `is_valid_body_format(jsonb)` are IMMUTABLE, read no data and are executable by `authenticated` and `service_role`, because a CHECK runs with the privileges of the role writing the row. The view `reports_to_review` (security_invoker, granted to no API role) is the moderation queue. Since `20261021090000`: `find_profile(text)`, `is_username_available(text)` and `touch_activity()` are SECURITY DEFINER with `search_path = ''`, executable by `authenticated` only, and reached through the public SECURITY INVOKER wrappers of the same names; `normalize_username(text)` and `is_reserved_username(text)` are IMMUTABLE helpers; the write-limit triggers (`quotes_enforce_limit`, `friendships_enforce_limits`, `shares_enforce_limit`, `reports_enforce_limit`) are SECURITY INVOKER and count the actor's own rows through RLS, while `events_enforce_limit` and `reports_snapshot_username` are SECURITY DEFINER; `purge_inactive_anonymous(timestamptz, integer)` is SECURITY DEFINER and executable by no API role; since `20261025090000`, `friend_favorites(uuid)` is SECURITY DEFINER, executable by `authenticated` only and reached through the public wrapper of the same name, and the trigger function `quotes_stamp_favorited_at` is executable by no client; and the tables `event_rate_limits` and `purge_runs` are granted to no API role. `service_role` (secret key) gets explicit table grants too. Supabase stops auto-granting new `public` tables to the Data API roles (new projects since 2026-05-30, all projects from 2026-10-30), so the migration's explicit grants are what expose the tables, locally and on hosted alike.

Client notes (these follow from the grants and policies above):
- `events` has no select grant, so inserts must not ask for the row back (supabase-swift `returning: .minimal`, PostgREST `Prefer: return=minimal`). The same applies to any insert whose row you could not read.
- The Rotation is written with `public.set_rotation(ordered uuid[], removed uuid[])` (migration `20261019070000_set_rotation`, called as `POST /rest/v1/rpc/set_rotation`). It is SECURITY INVOKER with `search_path = ''` and executable by `authenticated` and `service_role` only, so the quotes RLS policies and grants apply as for a direct UPDATE. One UPDATE gives the caller's own quotes in `ordered` positions 0…n-1 (first occurrence wins; IDs that are not the caller's or no longer exist are skipped without leaving a gap), sets `removed` to null (an ID in both lists stays in the Rotation), touches nothing else and returns the updated rows. Only IDs travel, in the POST body, so the request is small for any Rotation size, a quote deleted elsewhere is never re-inserted, and no content is written, so a stale copy on one device cannot undo an edit made on another. (It replaced a client-side upsert of whole rows, which an upsert needs because Postgres checks NOT NULL on the proposed insert before resolving the conflict.)
- Timestamps the client sends (`created_at`, `updated_at`, `seen_at`, `saved_at`) are replaced by the server clock, so read them back from the returned row rather than trusting the local `Date()`. Blank optional text must be sent as null; whitespace-only values fail a `*_not_blank` check with 23514 (the constraint name contains the column, for example `profiles_display_name_not_blank`).
- Profiles: look a stranger up with `POST /rest/v1/rpc/find_profile {"p_username": …}` (returns `id, username, display_name`, at most one row; none for your own username, for a blocked pair in either direction, or for a partial match; the input is trimmed, one leading `@` dropped and lowercased, like `Username.normalize`). Check a new username with `POST /rest/v1/rpc/is_username_available {"p_username": …}` (false when reserved, taken or invalid). A direct `select` on `profiles` returns only your own and linked rows. Embeds resolve for every list read (friendships both sides, inbox sender, sent recipient, blocked), but a row created by the same INSERT is not yet visible to the profiles policy, so `insert into friendships … returning` a request to a stranger embeds `addressee = null`; use the profile `find_profile` returned.
- Activity: call `POST /rest/v1/rpc/touch_activity` (no arguments, returns nothing) when the app comes to the foreground. It writes at most once per 12 hours. An anonymous account the app never touches is deleted after 365 days (section 7, Retention).
- Write limits: QR002 means an account total (5000 quotes), QR001 a rate (friend requests, pending requests, shares and reports per rolling 24 hours, events per clock hour). The message is short English (for example "You can share at most 100 quotes a day."), with a hint. PostgREST answers both with HTTP 400. Only rows that still exist count, so a cancelled, declined or blocked request, or a deleted share, frees its slot. An insert whose `id` already exists skips the quote and share limits, so a retry after a lost answer still fails with 23505 and can be resolved as before. A duplicate report fails with 23505 on `reports_reporter_reported_share_key`.
- Reporting then blocking: the block deletes the shares between the pair, so the report keeps `reported_user_id` and its content snapshot but its `share_id` becomes null. File the report before the block so the snapshot is the server's copy. `report(share:)` always sends the share's content, so if the share is already gone it falls back to a user report that still carries the content (as the reporter's app held it).

Why the content is snapshotted in `shares`: the recipient never needs RLS access to the sender's `quotes`. Edits and deletes by the sender don't silently change what was received. "Save" copies the snapshot into the recipient's `quotes` with `origin = 'shared'`.

**Verified quotes** (migrations `20261024090000_verified_quotes` and `20261028120000_catalog_corpus`). `quotes` and `shares` have `verified_starter_id integer null → catalog_quotes on delete set null` (the name predates the catalog and never changes: builds up to 6 select it): the catalog quote, not withdrawn, whose `body`, `author` and `source` the row matches exactly, found through the `md5(body)` index. A trigger (`quotes_set_verified`, `shares_set_verified`) computes it on insert and on every update of the text or of the column itself, so a client can never set it; editing the wording, author or source clears it, formatting does not, and a shared verified quote stays verified for the recipient and in their saved copy. The app shows the verified seal (`checkmark.seal.fill`, accent) at the end of the attribution line, and the quote detail's "Verified quote" sheet looks the id up in `catalog_quotes` (any status), names the work, `source_location` and the speaker, and opens `source_url`. Every catalog quote was checked word for word against that text (docs/catalog-sources.md; the starters also in docs/starter-pack-sources.md).

**The catalog and its batches** (plan: docs/catalog-population-plan.md). New verified quotes arrive in generated batch migrations, `<ts>_catalog_batch_NNN.sql`, at most 100 rows each (50 by default), each on its own branch `catalog/batch-NNN` so it reaches hosted only when merged. The verifier (`scripts/catalog.sh`, stdlib Python under `scripts/catalog/`) renders every body from the matched span of a pinned public-domain edition (never from a lead or a quote site), applies the public-domain rule computed from the date (US: the text used published in or before Y − 96; strict, for every App Store storefront: every contributor died in or before min(Y − 81, max(1951, Y − 101))) and the reject list, and must pass its gate (`qcat acceptance`) first. The founder keeps, themes and moods every line; `qcat generate batch` freezes the rows in `supabase/catalog/batches/NNN.jsonl` and writes the migration, which stages rows in temp tables, inserts with `on conflict (id) do nothing`, raises if a stored row differs (insert-or-verify, never update) and ends with `private.catalog_reseal(ids)`, so users' existing matching quotes gain the seal without moving `updated_at`. `qcat generate check` regenerates every batch and re-pin byte for byte from its snapshot, replays them in migration order, and requires `quotes.jsonl` and `works.jsonl` to hold exactly what they store. A live quote can be re-pinned when a better witness turns up (a Gutenberg text for an unscanned Wikisource page): `qcat generate repin` re-verifies it against its work's new pin, requires the same body, freezes the old and new provenance in `supabase/catalog/repins/NNN.jsonl` and writes `<ts>_catalog_repin_NNN.sql`, which updates only the provenance columns (`source_location`, `source_url`, `checked_*`, `match_kind`, `checked_at`, `verifier_version`) and the cited work's edition columns, compare-and-set from the emitted values, and fails if a row holds anything else. No seal moves, since id, body, author and source never change. A wrong row is fixed forward: `private.catalog_withdraw(id, reason)` takes the seal off every copy and `private.catalog_set_replacement(old, new)` names the correction; `private.catalog_unstar(id)` frees a retired starter's onboarding slot. None of these is executable by an API role. In the app, Verified Quotes (Library's + menu and the reminder picker) lists every live catalog quote by theme; onboarding offers only the starters; a quote added from the catalog gets `origin = 'catalog'` (starters keep `starter`).

**Favorites and profiles** (migration `20261025090000_favorites`, tests `15_favorites.test.sql`). The owner hearts a quote with a PATCH of `is_favorite`; the server owns `favorited_at`. `profiles.shows_favorites` is off by default and only the owner can change it (the profiles update policy). The quotes policies are unchanged, so a friend can never select another user's `quotes` rows. Instead `POST /rest/v1/rpc/friend_favorites {"p_user": …}` (public SECURITY INVOKER wrapper over `private.friend_favorites`, SECURITY DEFINER, `search_path = ''`, stable, executable by `authenticated` only) returns `id, body, body_format, author, source, verified_starter_id, favorited_at` for at most 100 of `p_user`'s favorites, newest first (`id` is `md5(quote id, viewer)` as a uuid: stable for that viewer, different for each, never the quote's primary key, so a friend can't use it to probe for the quote or insert a row under its id, for example during the owner's Undo), and nothing at all unless every one of these holds: the caller is signed in and is not `p_user`, `p_user` has `shows_favorites`, the two have an accepted friendship (either direction), and neither has blocked the other. A stranger, a pending request, an unfriended or blocked pair and the owner asking about themselves all get an empty list, the same answer as "no favorites", so the call reveals nothing about people you aren't friends with. Turning the setting off hides the favorites on the next read. The app's profile screen (`ProfileView`) also reads the friend's profile row (`shows_favorites`, so an empty list can say "keeps favorites private"). The profiles policy lets anyone linked to you read that flag (any friendship, a share or a block, as for the rest of the row); it is a preference, never a quote. `find_profile` does not return it, so a stranger's lookup can't see it, and the app's lookup asks only for `id, username, display_name` (asking for a column an RPC doesn't return fails with 42703). Undo of a delete re-inserts the quote, so a restored favorite gets a new `favorited_at`, like its new `created_at`. "Save" on a friend's favorite inserts a new quote with `origin = 'shared'`, like saving a share (the verified trigger recomputes `verified_starter_id`), and the app skips it when the library already holds the same text and author. Playlists (the Rotation) stay private: a profile shows favorites only (decision 2026-10-25, with the founder).

Why `rotation_position` is a column and not a join table: rotation membership is per user per quote, and only your own quotes can be in your Rotation. That means one table and one set of RLS policies. Reordering is a small bulk update. A new quote's position comes from the app's copy of the library (or a read of the end, for starter and shared saves), which can be stale or race another insert; the server moves a taken position to `max + 1` under the per-owner advisory lock that `quotes_enforce_limit` uses, so a new quote always joins the end. A free position is kept, so Undo of a delete returns the quote to its place (migration `20261021100000_rotation_position_on_insert`).

Reminder settings (times per day, window, weekdays, shuffle) are **device-local**, in App Group `UserDefaults`, because notifications are device-local too.

### Rich-text format, the `body_format` contract
`body` is plain text, which is what notifications, search, plain sharing and accessibility use. `body_format` is a normalized array of runs:
```json
[{"start":0,"length":13,"bold":true},{"start":40,"length":11,"underline":true}]
```
- `start` and `length` are **UTF-16 code units** in `body`. This is the same as `NSRange` and JavaScript.
- Runs are sorted, non-overlapping and non-empty. Adjacent runs with identical flags are merged. Each run has at least one true flag among `bold`, `italic` and `underline`; false flags are omitted.
- The server checks the shape (`private.is_valid_body_format`, used by `quotes`, `shares` and `catalog_quotes`): a JSON array of at most 200 runs; each run an object with integer `start` and `length` from 0 to 4000 (the most UTF-16 units a 2000-character body has) and optional boolean `bold`, `italic`, `underline`; no other keys; at most 16384 bytes as text. It does not check runs against `body`, sorting or overlap; that is the client's normalization.
- Clients must clamp runs to `body` when decoding, so bad data can never crash rendering.
- `QuotedCore.RichText` owns the conversions: runs ↔ `AttributedString` (for SwiftUI `Text` and widgets) and runs ↔ `NSAttributedString` (for the UITextView editor). Both are covered by round-trip unit tests.

## 4. API contracts (supabase-swift 2.55.x)
- Auth: `AuthService.signInAnonymously()` (`auth.signInAnonymously()`, `POST /auth/v1/signup` with no email) when no session is stored; it needs "Allow anonymous sign-ins" on the project, and `anonymous_provider_disabled` maps to "Quoted can't create your account right now: anonymous sign-ins are turned off on the server." `AuthService.sessionChanges` (from `auth.authStateChanges`) reports the signed-in user ID or nil. `AuthService.isAnonymous` reads `currentUser.isAnonymous`, and `currentEmail` is nil for an anonymous user (GoTrue sends `""`). Deletion is the `delete-account` function below, followed by a local `auth.signOut()`. DEBUG builds against a local stack can sign in with a password instead (section 5, Build configurations).
- Auth for email accounts (dormant until `AccountMode.current = .emailPassword`): `auth.signUp(email:password:redirectTo: quoted://auth-callback)`, `auth.signIn(email:password:)`, `auth.signOut()`, and `auth.session(from:)` for the `quoted://auth-callback` deep link. With PKCE, GoTrue redirects confirmation and password-reset links alike with only `?code=`, and supabase-swift emits `passwordRecovery` only for implicit-flow links, so `AuthService.handle(url:)` returns `AuthCallbackResult.passwordRecovery(id)` when the new access token's `amr` claim has `method: "recovery"` (or the URL has `type=recovery`), else `.signedIn(id)`.
- Redirects (email accounts only): Auth fixes an email link's `redirect_to` when it sends the email and checks it again when the link is opened. It keeps `quoted://auth-callback` only if that exact string is on the project's Redirect URLs (an entry without wildcards is an exact, case-sensitive match), otherwise it silently substitutes the Site URL. So the hosted project's Site URL and Redirect URLs are both `quoted://auth-callback` (section 10), and links from old emails or the dashboard open the app instead of localhost. `GET /verify` confirms the address before it redirects, so a link opened on another device (or after a failed code exchange) still confirms it, and the user can sign in with their password.
- PKCE window (email accounts only): the flow state for a sign-up or reset link expires 300 seconds (the GoTrue default) after the email was requested, not after it was opened. A later tap reaches the app, but `auth.session(from:)` fails with `flow_state_expired` (verified on the local stack). For sign-up the address is confirmed anyway; a reset link has to be requested again.
- Session storage: the Keychain, service `supabase.gotrue.swift`, account `sb-<project ref>-auth-token` (the SDK default, passed explicitly), written `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` by `DeviceKeychainStorage` so backups never carry the tokens to another device (items from older builds convert on their next write). Keychain items survive deleting the app, so the app calls `AuthService.clearLocalSession()` (no network) on the first launch after an install. For an anonymous account this Keychain item is the only key: there is no email or password to sign back in with. Deleting the app, moving to a new iPhone or a refresh token the server no longer accepts all start a new account, and the old account's rows stay on the server, unreachable, until the daily purge deletes the account (after 7 days without a username, or 365 days without activity; section 7, Retention).
- Lost sessions (anonymous accounts): `AppPreferences.hadAnonymousSession`, in `UserDefaults.standard` (which iOS deletes with the app), records that this install's last session was an anonymous account the user did not leave on purpose; Sign out and a successful Delete account clear it. When the SDK drops a session, or the server rejects one the SDK has already dropped, the app shows Welcome with "Your previous account can no longer be opened on this iPhone. Get started to begin again." (`SessionStore.lostAccountNotice`). A reinstall never shows it. A `.notSignedIn` answer while the SDK still holds the anonymous session keeps the account. Before the session is ready (no cached profile, or the empty-library check without the onboarding flag), the app refreshes the session once (`AuthService.refreshSession()`) and repeats the step, since the stored token can be rejected while the SDK still thinks it valid (a device clock running behind, or a rotated signing key). If the server no longer knows the session, the SDK drops it and Welcome shows the notice; if the refresh fails otherwise, the launch screen shows the error with Try again. Once the session is ready, the app stays where it is: background refreshes fail quietly and actions show the toast "Your session has ended. Try again in a moment." until the SDK refreshes or drops the session.
- Network: one `URLSession` from `Backend.makeURLSessionConfiguration()` (ephemeral, `urlCache = nil`, `.reloadIgnoringLocalCacheData`, no cookies or credential store) for Auth, PostgREST and Functions, so tokens and library, inbox and friend responses never reach `Library/Caches/…/Cache.db`. `Backend.purgeHTTPCaches()` empties `URLCache.shared`, which builds before this used; the app calls it at launch and on sign-out or account deletion.
- Data: PostgREST through `client.from("quotes")…`, returning typed `Codable` DTOs (snake_case keys through `CodingKeys`). List reads (`fetchMine`, `inbox`, `sent`, `friendships`, `blockedIDs`, `blockedProfiles`) page with `range(from:to:)`, 500 rows at a time with `count=exact`, until the count is reached, so nothing is cut at `max_rows` (1000). Rotation writes are one `set_rotation` RPC call carrying IDs only (see the client notes in section 3); deleting shares sends at most 100 IDs per request.
- Function: `client.functions.invoke("delete-account")` with the user's JWT. The function requires `POST`, verifies the user with `auth.getUser(jwt)`, and deletes with the service-role or secret key from function env (never in the app).
- Search: client-side, over the cached library and received shares. Case- and diacritic-insensitive, on body, author and source. Per-user data is small (at most a few thousand rows), so there are no round trips.

### State
`AppModel` (`@Observable @MainActor`) owns `SessionStore` (phase: `launching`, `signedOut`, `needsUsername`, `needsStarter` or `ready`; with anonymous accounts `signedOut` lasts only until the new account exists, so a fresh install goes from `launching` to `needsUsername`), `LibraryStore` (quotes, rotation, cache I/O) and `SocialStore` (profile, friends, requests, shares). Views read the stores. Mutations are `async` methods that update optimistically and roll back on error with a toast.

### Reminder planning (`ReminderPlanner`, pure and unit-tested)
Inputs are the ordered Rotation quote IDs, the settings (`timesPerDay` 1–12, `windowStart` < `windowEnd`, weekdays, shuffle), the rotation `anchor` date, `seed` and `startIndex` (`RotationState`, saved whenever the Rotation changes), `now`, and the calendar.
- **Slots:** for each enabled day, `n` times spread evenly from `windowStart` to `windowEnd`. With `n = 1` the slot is at `windowStart`.
- **Quote for a slot:** the slot's ordinal since `anchor`, plus `startIndex`, mod the count. For shuffle, that position indexes a permutation seeded by `seed`, so the order is the same on every replan.
- **Rotation and settings changes continue the cycle.** `RotationState.updated(with:at:seed:settings:previousSettings:calendar:)` keeps `anchor` and picks `startIndex` so the next slot plays the quote after the one shown last (the most recent slot's quote) in the new order. If that quote left the Rotation, the next one still in it (in the old order) plays; before any slot has passed, the upcoming quote stays next. The widget's "now" entry keeps showing the last quote. Adding, removing or reordering therefore never restarts at the top, so every quote is reached within one pass even when quotes are added often. A change to the schedule (times per day, window, days) or to In order / Shuffle does the same: the quote shown last is found under the settings the cycle ran under (`previousSettings`; `ReminderStore` keeps the settings of its last plan) and the next slot of the new schedule plays the one after it, instead of recounting every slot since the anchor under the new times, which landed anywhere in the cycle. Until the new schedule's first slot after the anchor, the widget shows the upcoming quote. A change to `enabled` alone keeps the state. States saved before `startIndex` existed decode with 0.
- **Output:** the next slots up to **60** (iOS caps an app at 64 pending; 4 are left as headroom). That is about 20 days at 3 a day. The app replans on launch, on foreground, and on any Rotation or settings change.
- The widget uses the same planner. Its timeline has one entry per upcoming slot in the next 24 hours, plus a "now" entry showing the most recent slot's quote, so **the widget always matches the last reminder**.

### Widget snapshot
`AppGroupStore` writes `widget-snapshot.json` (version, rotation quotes with runs, settings, anchor, seed, startIndex) to the App Group container and then calls `WidgetCenter.shared.reloadAllTimelines()`. With an empty Rotation the widget shows a friendly prompt and deep-links to Rotation.

### Deep links (`quoted://`)
`auth-callback` (email confirmation and password reset; email accounts only), `quote/<uuid>` (from a notification or widget), `rotation`.

### Build configurations
- `Debug`: hosted Supabase (default Run).
- `Debug-Local`: the local stack at `http://127.0.0.1:54321`, used for automated tests and development without touching production.
- `Release`: hosted.

The values come from `Config/*.xcconfig` and reach the app through Info.plist keys `SupabaseURL` and `SupabasePublishableKey`. Publishable keys are designed to ship in clients.

DEBUG-only password sign-in (for UI tests and `scripts/sign-in-local-demo.sh`): when the Supabase URL's host is `127.0.0.1` or `localhost`, the launch-environment variables `QUOTED_DEBUG_SIGNIN_EMAIL` and `QUOTED_DEBUG_SIGNIN_PASSWORD` make the app sign in with that email and password instead of creating an anonymous account, but only when no session is stored (for example after `-UITestReset`). A failure stays on the launch screen with Try again, with no anonymous fallback. With a stored session the variables are ignored, and Release builds or any build pointed at the hosted project never read them.

## 6. Security checklist
- RLS on every table. `with check` on every insert and update. UPDATE policies have matching SELECT policies.
- No `user_metadata` in authorization decisions.
- SECURITY DEFINER only in the unexposed `private` schema, with `search_path = ''` and an explicit `auth.uid()` or argument check, and execute granted only to `authenticated`.
- The service role and secret key live only in the Edge Function environment.
- After any schema change, check `supabase db advisors` for zero security findings.
- Deleting an account signs the user out locally right away. Access tokens expire within an hour (Supabase default). A retried delete whose first attempt already deleted the user (response lost) succeeds: when the function answers 401, `AccountService.deleteAccount()` asks `GET /auth/v1/user` with the stored token, and only a definite `user_not_found` counts as deleted; any other answer keeps the error (`notSignedIn`), so a real auth failure is never reported as a deletion. With email accounts (`AccountMode.emailPassword`) the user is then signed out on this device and asked to sign in again. An anonymous account keeps its session instead (signing out would lose it without deleting it), and the error asks the user to try again. If the SDK drops the anonymous session during the attempt, the account could not be deleted and stays on the server, unreachable; the app starts a new account and shows "Your session ended, so Quoted started a new account on this iPhone." (section 4, Lost sessions).
- Per-account write limits (BEFORE INSERT triggers, every role including the secret key): quotes 5000 per owner (QR002); friend requests 20 per rolling 24 hours and 50 pending (QR001); shares 100 per rolling 24 hours (QR001); reports 20 per rolling 24 hours and one per reporter, user and share (QR001, 23505); events 30 per clock hour (QR001). Each trigger takes a transaction-scoped advisory lock per actor, so concurrent requests from one account cannot overshoot, and runs VOLATILE, so it sees earlier rows of the same bulk insert. These cap what one account can do; they only multiply the number of accounts an attacker needs (at 5000 quotes of up to about 15 KB, roughly ten accounts fill a 500 MB free-tier database). The backstop is limiting how accounts are made (below) plus database-size alerts.
- Profiles are not a directory: an API caller can read only their own and linked profiles, and reaches anyone else only by exact username (`find_profile`), so the user list cannot be downloaded. A block is not revealed by a lookup or by a friend request's error. It can still be inferred from outside, because a fresh anonymous account (no block) can find the same username.
- Anonymous sign-in is open to anyone with the publishable key. Only the Auth rate limit holds it back (hosted default: 30 an hour per IP). Supabase recommends a CAPTCHA for it; there is none yet. Sign out is offered only with `AccountMode.emailPassword` to an account that is not anonymous, so this build offers it to no account.
- Session tokens stay on this device: Keychain `ThisDeviceOnly`, wiped on the first launch after an install, and never written to the HTTP cache (see section 4).

## 7. Scale and reliability
- Load: at MVP scale (≤10k users, a few hundred rows each), Postgres on the free tier is ample. Every foreign key is indexed, and `quotes(owner_id, created_at desc)` serves the library query.
- The app works offline for reading (cache, widgets and reminders are all local). Writes need a network and show an inline error. Creating the account needs a network; offline, Welcome shows the error under Get started. Lookups that run before a write (`nextRotationPosition`, the username lookup in `sendFriendRequest`) skip the SDK's GET retries (1 + 2 + 4 s), and the Rotation write has no lookup at all, so an offline write fails at once.
- Reminders keep firing with no network. They run out about 20 days after the last app open (accepted; see §9).
- Monitoring: Supabase logs and advisors; `events` count of `web_search_tap` decides whether to build in-app discovery.
- Moderation: the app promises that reports are reviewed within 24 hours, so the founder checks the queue every day in the dashboard SQL editor: `select * from private.reports_to_review;` (unreviewed reports, oldest first, with the reported username, whether the snapshot is server-verified and how many reports that user has). Act on each (delete the content, or the account under Authentication > Users), then `update public.reports set reviewed_at = now() where id = '<id>';`. While accounts are anonymous, deleting an account doesn't keep that person out: reinstalling the app creates a new account with a new username, and the blocks against the old account went with it. Optional alert: a Database Webhook (Integrations > Database Webhooks) on INSERT into `public.reports` that POSTs to an endpoint the founder controls; the payload is the whole report row, content included.
- Retention (council decision 2026-10-21): pg_cron job `purge-inactive-anonymous` runs `private.purge_inactive_anonymous()` daily at 03:17 UTC as postgres. It deletes from `auth.users` only anonymous accounts (`is_anonymous = true`): rule A, no profile and created more than 7 days ago; rule B, `last_active_at` more than 365 days ago and not `purge_exempt`. Email accounts are never touched. If more than `p_max_deletes` (default 500) accounts match, it deletes nothing and logs an aborted run. Every run is a row in `private.purge_runs` (`ran_at`, `rule_a_count`, `rule_b_count`, `aborted`): check it with `select * from private.purge_runs order by id desc limit 7;`, and the schedule with `select jobname, schedule, command from cron.job;`. The foreign keys do the rest, as for Delete account: profiles, quotes and the social rows go, reports stay with the ids set to null, and the username is free again. Rows are locked `FOR UPDATE SKIP LOCKED`, so an account being touched or creating its profile at that moment waits for the next run. Set `purge_exempt = true` (SQL editor) for anonymous accounts that must stay, such as the App Review helper. The migration schedules the job only where pg_cron is available (it is on hosted and on the local stack); elsewhere it applies with a warning. This is the one rule that tells anonymous accounts apart; access stays identical (pgTAP 10 and 12).
- Support: an anonymous account has no email, so nothing shows who owns it. Support must not delete an anonymous account on an emailed username alone; the owner deletes it in Account > Delete account.

## 8. Trade-offs (explicit)
| Decision | Chosen | Alternative | Why |
|---|---|---|---|
| Reminders | Local notifications | APNs and a cron sender | $0, no server, works offline. The cost is no cross-device sync and the 64-pending cap. |
| Rich text storage | Plain `body` plus UTF-16 runs | Markdown or HTML | Lossless for B/I/U, trivially searchable and pushable, safe to render. |
| Search | Client-side plus a Google link-out | FTS RPC or a quote API | Instant, offline, no vendor or cost. Revisit past about 5k quotes per user. |
| Share content | Snapshot | A reference to the sender's row | Simpler RLS, stable for the recipient. Costs a little duplicate storage. |
| Editor | UITextView representable | iOS 26 rich `TextEditor` | Mature attribute APIs (font traits, underline) and precise toolbar toggling. Revisit as SwiftUI matures. |
| Accounts | An anonymous Supabase account per iPhone | Email sign-in, a local-only app, one shared demo account | No email setup blocks testing, and RLS, friends and sharing stay as they are. The costs: no recovery after a reinstall, no sign-out, and weaker bans (docs/decisions/2026-10-20-anonymous-accounts.md). |
| Account delete | Edge Function with admin API | SECURITY DEFINER SQL deleting `auth.users` | The documented, supported path. Keeps the service role off the database API surface. |
