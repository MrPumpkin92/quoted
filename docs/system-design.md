## 1. Requirements

### Functional
| # | Requirement | MVP behaviour |
|---|---|---|
| F1 | Accounts | No sign-in screens (docs/decisions/2026-10-20-anonymous-accounts.md). With no stored session the app creates an anonymous Supabase Auth account for this iPhone (`signInAnonymously`), then asks for a username (handle). Sign out is offered only with `AccountMode.emailPassword` to an account that is not anonymous, so this build has none, not even for a leftover or DEBUG email session. In-app account deletion (App Store 5.1.1(v)), after which the app starts a new, empty account. Email and password sign-up and sign-in stay in the code, switched off (`AccountMode.current` in `App/Stores/SessionStore.swift`). |
| F2 | Quotes | Create, edit and delete quotes: text, author, source. Rich text supports **bold**, *italic* and <u>underline</u>. |
| F3 | Rotation | An ordered subset of the user's own quotes (the "playlist"). The user can reorder it and switch between in-order and shuffle. |
| F4 | Reminders | Local notifications cycle through the Rotation, N times a day, spaced evenly inside a time window on chosen weekdays. |
| F5 | Widgets | Home-screen widgets (small and medium) and a Lock Screen rectangular widget show the current Rotation quote, matching the latest reminder. |
| F6 | Friends | Add a friend by exact username (sends a request), accept or decline, unfriend, block. |
| F7 | Sharing | Send a quote to one or more friends with an optional note. The recipient sees it under "Shared with you" and can save it to their library, report it or block the sender. Plain-text sharing to any app goes through the system share sheet. |
| F8 | Search | A `.searchable` bar over the library and shared quotes. The last row reads "Search the web for '<term>' quotes" and opens Google in an in-app browser (`SFSafariViewController`; this counts as unrestricted web access for the age rating, see docs/decisions/2026-10-19-web-search-browser.md). A `PasteButton` in Add brings a copied quote back. Taps on the web row are logged. |
| F9 | Starter pack | About 60 public-domain quotes with checked attributions. During onboarding the user picks some; they are copied into the library and the Rotation. |
| F10 | Favorites and profiles | Heart any of your quotes (detail and full-screen toolbars, Library swipe and context menu; Library can show only favorites). Your profile (Account > Your profile) lists your favorites and has "Show favorites to friends", off by default. A friend's profile (from Friends) shows their favorites, newest first, only when they turned that on, with Save to copy one into your library. Reminders and every other quote stay private. |

### Non-functional
- **Native and smooth.** SwiftUI on iOS 26+, 60/120 fps scrolling, no spinners on launch. The library loads from a local cache and then refreshes.
- **Secure by default.** RLS on every exposed table. The client holds only the publishable key. Server state is never trusted from the client.
- **Cheap.** $0 at MVP scale (Supabase free tier, no paid APIs, no push server).
- **App Store ready.** Privacy manifest, account deletion, UGC report and block (1.2), export compliance, app icon, versioning.

### Constraints
- A solo founder. Ship the MVP fast and keep the moving parts few.
- Supabase project `yyajndbishiyugtbpzmk`, with a publishable key in the client.
- No Google search API is available: Custom Search JSON API is closed to new customers and ends 2027-01-01.

### Data flow, main paths
1. **Launch.** Restore the session from the Keychain. With none (a fresh install, right after deleting the account, or after a lost session, section 4), show Welcome; Get started creates an anonymous account with `auth.signInAnonymously()` and shows Choose a username, and a failure (offline, or anonymous sign-ins off on the server) shows inline under Get started. With a session, render the library from the App Group cache, then refresh it from Postgres. Plan reminders and write the widget snapshot, then reload widget timelines. A launch step that fails before the session is ready (no cached profile, or the empty-library check without the onboarding flag) shows the error on the launch screen with Try again, and the app retries by itself: after 3, 10 and then every 30 seconds while the screen shows, and at once when it returns to the foreground. DEBUG builds print the diagnostic and the Supabase URL under the button.
2. **Save a quote.** Validate on the client. `insert` returns the row and updates the cache. If it is in the Rotation, re-plan reminders and the widget.
3. **Reminder fires.** iOS delivers the local notification and no code runs. A tap deep-links to `quoted://quote/<id>`.
4. **Send.** `open_conversation(friend)`, then `insert into messages` with the source (`source_quote_id`, `starter_quote_id`, or, to forward someone else's quote, `source_post_id` or `source_message_id`; or text, or a playlist), never the content: a trigger builds the snapshot. RLS checks membership, an open conversation, an accepted friendship, no block, accepted terms and no suspension. The recipient sees it on the next refresh (polling while the conversation is open, on foreground and on pull to refresh).
5. **Delete account.** Call `functions.invoke("delete-account")`. The function verifies the JWT and calls `auth.admin.deleteUser`, and FK cascades remove the user's rows (reports are kept for moderation with the user's id set to null; events never carry a user id). The client then signs out, wipes the cache and snapshot, and removes pending notifications. With anonymous accounts it then creates a new, empty account and shows Choose a username.

## 3. Data model (Postgres, `public` schema)

`profiles.id` and `quotes.owner_id` reference `auth.users(id) on delete cascade`. The social tables (`friendships`, `blocks`, `playlists`, `posts`, `conversations`, `conversation_members`, `messages`) reference `profiles(id) on delete cascade` instead. This lets PostgREST embed the other party's profile (`sender:profiles!messages_sender_id_fkey(username, display_name)`) in one request, and deleting an auth user still cascades through `profiles`. `reports` also references `profiles`, but `on delete set null`, so a report outlives the deletion of either account (moderation evidence). Provenance ("Added by") lives in two pairs, `creator_id, creator_username` and `edited_from_id, edited_from_username`, on `quotes`, `posts` and `messages`: each pair is one composite foreign key to `profiles (id, username)` `on delete set null`, so deleting an account clears both columns and the row reads "Added by a person". `events` has no user column at all. Every table has RLS enabled and explicit grants to `authenticated` only (nothing to `anon`). Policies use `(select auth.uid())`, which is evaluated once per statement.

Anonymous accounts are ordinary Auth users. Their JWT has the role `authenticated` and the claim `is_anonymous: true`. The policies deliberately don't look at that claim, so an anonymous user has exactly the access an email user has: their own rows, their friends and the conversations between them. `supabase/tests/database/10_anonymous_user.test.sql` proves the parity. The `anon` role (the publishable key with no session) still gets nothing.

The server owns every timestamp: BEFORE INSERT triggers (`<table>_stamp_created_at`) set `created_at` to the server clock whatever the client sends, `profiles` and `quotes` keep `created_at` on update (`<table>_keep_created_at`), and the other timestamps are noted per table below. Text the app trims must contain something other than whitespace on the server too (`<table>_<column>_not_blank` checks through `private.is_blank`, which strips exactly Unicode White_Space, the set Swift trims, so the server is never stricter than the app).

Implemented in `supabase/migrations/20261019040000_core_schema.sql` (plus `20261019050000_report_snapshot.sql` for the report snapshot, `20261019060000_hardening.sql` for the format, text and timestamp checks, anonymous events and report retention, and `20261021090000_abuse_limits_privacy_cleanup.sql` for profile privacy, write limits, immutable and reserved usernames, block privacy, activity and the purge of abandoned anonymous accounts; the social redesign adds `20261029090000_provenance_and_accounts.sql`, `20261029090100_playlists.sql`, `20261029090200_posts.sql`, `20261029090300_conversations_and_messages.sql`, `20261029090400_profiles_and_moderation.sql`, `20261029090500_forward_quotes.sql` and `20261029090600_read_marks_reports_playlist_order.sql`) and covered by `supabase/tests/database/*.test.sql`. Foreign keys are named `<table>_<column>_fkey` (for example `messages_sender_id_fkey`, `posts_author_id_fkey`, `friendships_requester_id_fkey`, `friendships_addressee_id_fkey`), so embedding hints are stable.

Client notes (these follow from the grants and policies above):
- `events` has no select grant, so inserts must not ask for the row back (supabase-swift `returning: .minimal`, PostgREST `Prefer: return=minimal`). The same applies to any insert whose row you could not read.
- The Rotation is written with `public.set_rotation(ordered uuid[], removed uuid[])` (migration `20261019070000_set_rotation`, called as `POST /rest/v1/rpc/set_rotation`). ### Rich-text format, the `body_format` contract
`body` is plain text, which is what notifications, search, plain sharing and accessibility use. `body_format` is a normalized array of runs:
```json
[{"start":0,"length":13,"bold":true},{"start":40,"length":11,"underline":true}]
```
- `start` and `length` are **UTF-16 code units** in `body`. This is the same as `NSRange` and JavaScript.
- Runs are sorted, non-overlapping and non-empty. Adjacent runs with identical flags are merged. Each run has at least one true flag among `bold`, `italic` and `underline`; false flags are omitted.
- The server checks the shape (`private.is_valid_body_format`, used by `quotes`, `posts`, `messages` and `starter_quotes`): a JSON array of at most 200 runs; each run an object with integer `start` and `length` from 0 to 4000 (the most UTF-16 units a 2000-character body has) and optional boolean `bold`, `italic`, `underline`; no other keys; at most 16384 bytes as text. It does not check runs against `body`, sorting or overlap; that is the client's normalization.
- Clients must clamp runs to `body` when decoding, so bad data can never crash rendering.
- `QuotedCore.RichText` owns the conversions: runs ↔ `AttributedString` (for SwiftUI `Text` and widgets) and runs ↔ `NSAttributedString` (for the UITextView editor). Both are covered by round-trip unit tests.

## 4. API contracts (supabase-swift 2.55.x)
- Auth: `AuthService.signInAnonymously()` (`auth.signInAnonymously()`, `POST /auth/v1/signup` with no email) when no session is stored; it needs "Allow anonymous sign-ins" on the project, and `anonymous_provider_disabled` maps to "Quoted can't create your account right now: anonymous sign-ins are turned off on the server." `AuthService.sessionChanges` (from `auth.authStateChanges`) reports the signed-in user ID or nil. `AuthService.isAnonymous` reads `currentUser.isAnonymous`, and `currentEmail` is nil for an anonymous user (GoTrue sends `""`). Deletion is the `delete-account` function below, followed by a local `auth.signOut()`. DEBUG builds against a local stack can sign in with a password instead (section 5, Build configurations).
- Auth for email accounts (dormant until `AccountMode.current = .emailPassword`): `auth.signUp(email:password:redirectTo: quoted://auth-callback)`, `auth.signIn(email:password:)`, `auth.signOut()`, and `auth.session(from:)` for the `quoted://auth-callback` deep link. With PKCE, GoTrue redirects confirmation and password-reset links alike with only `?code=`, and supabase-swift emits `passwordRecovery` only for implicit-flow links, so `AuthService.handle(url:)` returns `AuthCallbackResult.passwordRecovery(id)` when the new access token's `amr` claim has `method: "recovery"` (or the URL has `type=recovery`), else `.signedIn(id)`.
- Redirects (email accounts only): Auth fixes an email link's `redirect_to` when it sends the email and checks it again when the link is opened. It keeps `quoted://auth-callback` only if that exact string is on the project's Redirect URLs (an entry without wildcards is an exact, case-sensitive match), otherwise it silently substitutes the Site URL. So the hosted project's Site URL and Redirect URLs are both `quoted://auth-callback` (section 10), and links from old emails or the dashboard open the app instead of localhost. `GET /verify` confirms the address before it redirects, so a link opened on another device (or after a failed code exchange) still confirms it, and the user can sign in with their password.
- PKCE window (email accounts only): the flow state for a sign-up or reset link expires 300 seconds (the GoTrue default) after the email was requested, not after it was opened. A later tap reaches the app, but `auth.session(from:)` fails with `flow_state_expired` (verified on the local stack). For sign-up the address is confirmed anyway; a reset link has to be requested again.
- Session storage: the Keychain, service `supabase.gotrue.swift`, account `sb-<project ref>-auth-token` (the SDK default, passed explicitly), written `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` by `DeviceKeychainStorage` so backups never carry the tokens to another device (items from older builds convert on their next write). Keychain items survive deleting the app, so the app calls `AuthService.clearLocalSession()` (no network) on the first launch after an install. For an anonymous account this Keychain item is the only key: there is no email or password to sign back in with. Deleting the app, moving to a new iPhone or a refresh token the server no longer accepts all start a new account, and the old account's rows stay on the server, unreachable, until the daily purge deletes the account (after 7 days without a username, or 365 days without activity; section 7, Retention).
- Lost sessions (anonymous accounts): `AppPreferences.hadAnonymousSession`, in `UserDefaults.standard` (which iOS deletes with the app), records that this install's last session was an anonymous account the user did not leave on purpose; Sign out and a successful Delete account clear it. When the SDK drops a session, or the server rejects one the SDK has already dropped, the app shows Welcome with "Your previous account can no longer be opened on this iPhone. Get started to begin again." (`SessionStore.lostAccountNotice`). A reinstall never shows it. A `.notSignedIn` answer while the SDK still holds the anonymous session keeps the account. Before the session is ready (no cached profile, or the empty-library check without the onboarding flag), the app refreshes the session once (`AuthService.refreshSession()`) and repeats the step, since the stored token can be rejected while the SDK still thinks it valid (a device clock running behind, or a rotated signing key). If the server no longer knows the session, the SDK drops it and Welcome shows the notice; if the refresh fails otherwise, the launch screen shows the error with Try again. Once the session is ready, the app stays where it is: background refreshes fail quietly and actions show the toast "Your session has ended. Try again in a moment." until the SDK refreshes or drops the session.
- Network: one `URLSession` from `Backend.makeURLSessionConfiguration()` (ephemeral, `urlCache = nil`, `.reloadIgnoringLocalCacheData`, no cookies or credential store) for Auth, PostgREST and Functions, so tokens and library, inbox and friend responses never reach `Library/Caches/…/Cache.db`. `Backend.purgeHTTPCaches()` empties `URLCache.shared`, which builds before this used; the app calls it at launch and on sign-out or account deletion.
- Data: PostgREST through `client.from(…)`, returning typed `Codable` models (snake_case keys through `CodingKeys`). Every read names its columns (`Columns` in `QuotedKit/Data/Rows.swift`); `posts`, `messages`, `profiles` and `reports` are never read with `*` and never select a column without a select grant (`source_*`, private profile fields, `content_*`). Writes send only granted columns, with explicit nulls only where the column is granted: a quote insert sends `id, body, body_format, author, source, origin, rotation_position`, plus `is_favorite` for the Undo insert (owner, creator and edited-from are the server's), a profile insert `id, username, display_name`, and a message insert only the columns its kind uses. Inserts carry client-chosen ids, so a retry after a lost answer reads the first row back on 23505 instead of writing twice (quotes, posts, messages, playlists). List reads (`fetchMine`, `friendships`, `blockedIDs`, `blockedUsers`, `mine` playlists) page with `range(from:to:)`, 500 rows at a time with `count=exact`, until the count is reached, so nothing is cut at `max_rows` (1000). The Feed and a conversation page by keyset, newest first (`created_at desc, id`, `PageCursor`), 50 messages per page; `receivedQuotes()` (every quote message sent to you, across conversations: `received_quotes`, never a filter on the `messages` table) pages the same way, 500 at a time, to the end. The read-only RPCs (`my_account`, `inbox_conversations`, `received_quotes`, `profile_view`) go as GET (`SupabaseClient.readRPC`), because supabase-swift retries only GET and HEAD (1, 2 and 4 s after a dropped connection, a 503 or a 520); the terms check before a write reads `my_account` without retries, so offline fails at once. Rotation writes are one `set_rotation` RPC call carrying IDs only (see the client notes in section 3).
- Repositories (`Backend`, one per area, each a `Sendable` struct over the shared `SupabaseClient`): `quotes` (your library; `addCatalogQuotes` → `add_catalog_quotes`; `save(SnapshotRef)` → `save_from_post`, `save_from_message`, `save_from_favorite`, `save_from_playlist` or `add_catalog_quotes`, each keeping the creator; `restore` is the Undo insert with the same id), `profiles` (`my_account`, `accept_terms`, `createProfile`, display name, "Friends can text me", `favorites_visibility`, `profile_view`, `friend_favorites`, `find_profile`, `is_username_available`, `touch_activity`), `social` (friendships and blocks), `posts` (Feed, a person's posts, create, audience, delete), `messages` (`open_conversation`, `inbox_conversations`, a conversation's page, the quote messages you received across conversations, send, unsend, mark read up to a time, Delete Conversation), `playlists` (yours, `playlist_view`, items with spaced positions reordered in one `set_playlist_positions` call, `save_playlist_copy`) and `reports` (a post, message, playlist, catalog quote or profile; when the target is gone, a profile report with what the app showed, unless you already filed one about that target), plus `starter`, `events` and `account`.
- Messages: a quote travels by reference (`QuoteRef`: your quote, a catalog id, or to forward, a post or a quote message), never by its words; the server builds the snapshot and its creator. Mark read sets your `conversation_members.last_read_at` to the time of the newest message you have shown (the server keeps it up to its own clock), so a message that arrived after your last refresh stays unread; Delete Conversation sets `cleared_at` (the server clock). The Inbox badge counts `inbox_conversations().unread_count` (`InboxBadge`); there is no push or Realtime, so the app refreshes on foreground, on pull to refresh and on screen appear.
- Errors (`QuotedError`): terms and suspension 42501s map to `.termsRequired` and `.suspended` before any per-call mapping; `This conversation is closed.` to `.conversationClosed`; `… is not available.` to `.unavailable(message)`; any other 42501 sentence the server wrote for people (capital letter, full stop) to `.validation(message)`, shown as it is; Postgres's own messages to `.server` (never shown). QR003 is `.blockedWords` (field-specific copy for names and playlist titles), QR004 `.textsOff`, QR001 and QR002 the server's sentence.
- Terms in the app: `SocialStore.requireTerms(for:then:)` runs a friend request, an accept or a send once `my_account()` says the current terms are accepted (a cached yes is trusted; anything else asks the server). Otherwise the Terms sheet (`.termsSheet()`, on the root and inside `SheetHost`, docs/ui-spec.md §22) stacks over the screen that asked; Accept calls `accept_terms(current_terms_version)` and runs the write, Not Now drops it. A write refused with `.termsRequired` makes the next check ask the server. The check belongs to the screen or sheet that asked (`for:`): when it goes away first (`dropTermsChecks(for:)` from its `onDisappear`), the server's answer shows nothing and runs nothing, and a write of it waiting on the Terms sheet is dropped, so a send the user cancelled never comes back as a Terms sheet over another screen. The control shows progress through the check (Send keeps its sheet open meanwhile; Accept ignores further taps and turns Decline off).
- Function: `client.functions.invoke("delete-account")` with the user's JWT. The function requires `POST`, verifies the user with `auth.getUser(jwt)`, and deletes with the service-role or secret key from function env (never in the app).
- Search: client-side, over the cached library and the loaded messages (`SearchIndex(quotes:inbox:)`: a quote message's body, author, source and note, a text, a playlist's title). Today's Search shows the received quote messages as "Shared with you". Case- and diacritic-insensitive. Per-user data is small (at most a few thousand rows), so there are no round trips.

### State
`AppModel` (`@Observable @MainActor`) owns `SessionStore` (phase: `launching`, `signedOut`, `needsUsername`, `needsStarter` or `ready`; with anonymous accounts `signedOut` lasts only until the new account exists, so a fresh install goes from `launching` to `needsUsername`; the profile and `MyAccount` from `my_account()`, both cached per user, which hold favorites visibility and the accepted terms version), `LibraryStore` (quotes, rotation, cache I/O; catalog quotes through `add_catalog_quotes`, other people's quotes through the `save_from_*` functions) and `SocialStore` (friends, requests, blocks, reports, the Terms gate, and the quotes friends sent). Views read the stores. Mutations are `async` methods that update optimistically and roll back on error with a toast.

Until the Inbox and conversation screens (Stage 5), each `SocialStore` refresh makes three reads, whatever the number of conversations: friendships, `inbox_conversations()` (the sender's profile and your read mark for each conversation) and `receivedQuotes()` (`received_quotes`), every quote message sent to you, read to the end ("Shared with you", Search, the Library and Friends rows, the background alert, the App Group cache). Reading them all each time means no busy conversation hides older quotes, and a quote its sender unsent leaves at the next refresh. A quote is unseen while it is newer than your `last_read_at` in its conversation; opening Friends or "Shared with you" marks each conversation holding an unseen quote read up to the newest quote the app shows from it (`InboxConversation.seenMarks`), never further: the Inbox row's latest message may be a text or a quote that arrived after the quotes were read, which the app has not shown, so it stays unread (the local row keeps an unread count until the next refresh). A quote you report loses Save at once, and its card goes once the "Also block?" offer is answered. Blocked users lists someone who blocked you back without a profile ("Blocked account"), so you can still unblock them; its Unblock confirmation promises nothing about what they can do, since their own block still keeps you apart (`is_blocked_pair` is symmetric). Saved means the library holds the same text and author (`saved_at` is gone). Send opens each friend's conversation and sends one quote message per friend with its own id; Undo unsends them. Profiles of other people come from `profile_view`. These stopgaps go when the new screens land.

### Reminder planning (`ReminderPlanner`, pure and unit-tested)
Inputs are the ordered Rotation quote IDs, the settings (`timesPerDay` 1–12, `windowStart` < `windowEnd`, weekdays, shuffle), the rotation `anchor` date, `seed` and `startIndex` (`RotationState`, saved whenever the Rotation changes), `now`, and the calendar.
- **Slots:** for each enabled day, `n` times spread evenly from `windowStart` to `windowEnd`. With `n = 1` the slot is at `windowStart`.
- **Quote for a slot:** the slot's ordinal since `anchor`, plus `startIndex`, mod the count. For shuffle, that position indexes a permutation seeded by `seed`, so the order is the same on every replan.
- **Rotation and settings changes continue the cycle.** `RotationState.updated(with:at:seed:settings:previousSettings:calendar:)` keeps `anchor` and picks `startIndex` so the next slot plays the quote after the one shown last (the most recent slot's quote) in the new order. If that quote left the Rotation, the next one still in it (in the old order) plays; before any slot has passed, the upcoming quote stays next. The widget's "now" entry keeps showing the last quote. Adding, removing or reordering therefore never restarts at the top, so every quote is reached within one pass even when quotes are added often. A change to the schedule (times per day, window, days) or to In order / Shuffle does the same: the quote shown last is found under the settings the cycle ran under (`previousSettings`; `ReminderStore` keeps the settings of its last plan) and the next slot of the new schedule plays the one after it, instead of recounting every slot since the anchor under the new times, which landed anywhere in the cycle. Until the new schedule's first slot after the anchor, the widget shows the upcoming quote. A change to `enabled` alone keeps the state. States saved before `startIndex` existed decode with 0.
- **Output:** the next slots up to **60** (iOS caps an app at 64 pending; 4 are left as headroom). That is about 20 days at 3 a day. The app replans on launch, on foreground, and on any Rotation or settings change.
- The widget uses the same planner. Its timeline has one entry per upcoming slot in the next 24 hours, plus a "now" entry showing the most recent slot's quote, so **the widget always matches the last reminder**.

### Widget snapshot
`AppGroupStore` writes `widget-snapshot.json` (version, rotation quotes with runs, settings, anchor, seed, startIndex) to the App Group container and then calls `WidgetCenter.shared.reloadAllTimelines()`. With an empty Rotation the widget shows a friendly prompt and deep-links to Rotation.

### Deep links (`quoted://`)
`auth-callback` (email confirmation and password reset; email accounts only), `quote/<uuid>` (from a notification or widget), `rotation`.

### Build configurations

- `Debug-Local`: the local stack at `http://127.0.0.1:54321`, used for automated tests and development without touching production.
- `Release`: hosted.

The values come from `Config/*.xcconfig` and reach the app through Info.plist keys `SupabaseURL` and `SupabasePublishableKey`. Publishable keys are designed to ship in clients.

DEBUG-only password sign-in (for UI tests and `scripts/sign-in-local-demo.sh`): when the Supabase URL's host is `127.0.0.1` or `localhost`, the launch-environment variables `QUOTED_DEBUG_SIGNIN_EMAIL` and `QUOTED_DEBUG_SIGNIN_PASSWORD` make the app sign in with that email and password instead of creating an anonymous account, but only when no session is stored (for example after `-UITestReset`). A failure stays on the launch screen with Try again, with no anonymous fallback. ## 6. Security checklist
- RLS on every table. `with check` on every insert and update. UPDATE policies have matching SELECT policies.
- No `user_metadata` in authorization decisions.
- SECURITY DEFINER only in the unexposed `private` schema, with `search_path = ''` and an explicit `auth.uid()` or argument check, and execute granted only to `authenticated`.
- The service role and secret key live only in the Edge Function environment.
- After any schema change, check `supabase db advisors` for zero security findings.
- Deleting an account signs the user out locally right away. Access tokens expire within an hour (Supabase default). A retried delete whose first attempt already deleted the user (response lost) succeeds: when the function answers 401, `AccountService.deleteAccount()` asks `GET /auth/v1/user` with the stored token, and only a definite `user_not_found` counts as deleted; any other answer keeps the error (`notSignedIn`), so a real auth failure is never reported as a deletion. With email accounts (`AccountMode.emailPassword`) the user is then signed out on this device and asked to sign in again. An anonymous account keeps its session instead (signing out would lose it without deleting it), and the error asks the user to try again. If the SDK drops the anonymous session during the attempt, the account could not be deleted and stays on the server, unreachable; the app starts a new account and shows "Your session ended, so Quoted started a new account on this iPhone." (section 4, Lost sessions).
- Per-account write limits (BEFORE INSERT triggers, every role including the secret key): quotes 5000 per owner (QR002); friend requests 20 per rolling 24 hours and 50 pending (QR001); accepted friends 150 per person (QR002); posts 20 per rolling 24 hours (QR001); messages 300 per rolling 24 hours (QR001); playlists 20 new per rolling 24 hours (QR001), 100 per owner and 200 items each (QR002); reports 20 per rolling 24 hours and one per reporter, user and target (QR001, 23505); events 30 per clock hour (QR001). Each trigger takes a transaction-scoped advisory lock per actor (playlist items lock their playlist row), so concurrent requests from one account cannot overshoot, and runs VOLATILE, so it sees earlier rows of the same bulk insert. These cap what one account can do; they only multiply the number of accounts an attacker needs (at 5000 quotes of up to about 15 KB, roughly ten accounts fill a 500 MB free-tier database). The backstop is limiting how accounts are made (below) plus database-size alerts.
- Profiles are not a directory: an API caller can read only their own and linked profiles (four columns), and reaches anyone else only by exact username (`find_profile`, `profile_view`), so the user list cannot be downloaded.
- Provenance is a server fact: no client writes a creator, an edited-from, an origin other than manual or pasted, a snapshot, a verification, a hold or a timestamp. The column grants refuse them (42501) and the triggers rebuild them, so nobody can put words under another person's username.
- Social writes need the current Terms of use and no suspension (42501), checked by the policies and, first, by the triggers, so the refusal is the same whatever the target. Public ("Anyone with your username") also needs `private.can_publish()`, false for everyone until Sign in with Apple linking ships, and an eligible quote, so other people's usernames never reach strangers without their opt-in. The gate holds on every read too: a public item reaches strangers only while its owner may still publish (an unlinked Apple identity or terms that moved on hide it again from strangers, not from friends). Verified quotes travel with no creator or edited-from at all (posts, messages and saved copies).
- Only the two members of a conversation can read or send in it, through every table and RPC (`19_conversations_messages.test.sql`); strangers get zero posts and playlists (`18`, `17`, `21`).
- Word filter (QR003) on every text another person can see: display names, new usernames, captions, message text and notes, playlist titles and unverified snapshots; live views (`friend_favorites`, `playlist_view`) skip unverified items that match at read time. Never on the private Library. The list lives only on the server (`private.blocked_terms`), and is matched as one pattern (`private.blocked_term_pattern`), so the cost of a check hardly grows with the list. Text is folded before matching (`private.filter_fold`): fullwidth and styled letters, accents, zero-width and other invisible characters, common Cyrillic and Greek look-alikes, and any separator inside a phrase do not get a term past it. Spaced-out letters and other homoglyphs still can. A playlist title or display name written before a term was added keeps showing (only items are re-checked at read time). A block is not revealed by a lookup or by a friend request's error. It can still be inferred from outside, because a fresh anonymous account (no block) can find the same username.
- Anonymous sign-in is open to anyone with the publishable key. Only the Auth rate limit holds it back (hosted default: 30 an hour per IP). Supabase recommends a CAPTCHA for it; there is none yet. Sign out is offered only with `AccountMode.emailPassword` to an account that is not anonymous, so this build offers it to no account.
- Session tokens stay on this device: Keychain `ThisDeviceOnly`, wiped on the first launch after an install, and never written to the HTTP cache (see section 4).

## 7. Scale and reliability
- Load: at MVP scale (≤10k users, a few hundred rows each), Postgres on the free tier is ample. Every foreign key is indexed, and `quotes(owner_id, created_at desc)` serves the library query.
- The app works offline for reading (cache, widgets and reminders are all local). Writes need a network and show an inline error. Creating the account needs a network; offline, Welcome shows the error under Get started. Lookups that run before a write (`nextRotationPosition`, the username lookup in `sendFriendRequest`) skip the SDK's GET retries (1 + 2 + 4 s), and the Rotation write has no lookup at all, so an offline write fails at once.
- Reminders keep firing with no network. They run out about 20 days after the last app open (accepted; see §9).
- Monitoring: Supabase logs and advisors; `events` count of `web_search_tap` decides whether to build in-app discovery.
- Moderation: the app promises that reports are reviewed within 24 hours, so the founder checks the queue every day in the dashboard SQL editor: `select * from private.reports_to_review;` (unreviewed reports, oldest first). Each row says what was reported (`target_kind`: message, post, playlist, catalog_quote or profile, with its id; `target_deleted` when the message was unsent or the post or playlist deleted, and an unsent message stays in `private.message_tombstones` for 30 days), whether the target is held (`target_held_at`) and how many people reported it (`target_reporters`), the server's copy (`content_body`, `content_author`, `content_source`, `content_note`) and whether it is verified, and the people involved (the reported username, whether that account is deleted or suspended, how many reports it has (`reports_against_user`) and from how many different people (`reporters_against_user`; one account files at most 3 profile reports a day about one person), and the reporter). Two different reporters hold a post or playlist automatically (hidden from everyone but its owner). Act on each: clear a hold you checked (`update public.posts set held_at = null where id = '<id>';`, or `public.playlists`), delete the content, suspend the account with `select * from private.suspend_user('<user id>', '<reason>');` (every social write is refused and all their posts and playlists are held; it returns how many it held; while suspended, their favorites are hidden from friends too) or delete it under Authentication > Users (its username is retired for good). `select private.unsuspend_user('<user id>');` ends a suspension and leaves the held items held for you to clear one by one. Then `update public.reports set reviewed_at = now() where id = '<id>';`. No API role can run `suspend_user`, `unsuspend_user` or read the queue. While accounts are anonymous, neither a suspension nor a deletion keeps that person out: reinstalling the app creates a new account with a new username, and the blocks against the old account went with it (bans tied to a hashed Apple identity come with Sign in with Apple). Optional alert: a Database Webhook (Integrations > Database Webhooks) on INSERT into `public.reports` that POSTs to an endpoint the founder controls; the payload is the whole report row, content included.
- Retention (council decision 2026-10-21): pg_cron job `purge-inactive-anonymous` runs `private.purge_inactive_anonymous()` daily at 03:17 UTC as postgres. It deletes from `auth.users` only anonymous accounts (`is_anonymous = true`): rule A, no profile and created more than 7 days ago; rule B, `last_active_at` more than 365 days ago and not `purge_exempt`. Email accounts are never touched. If more than `p_max_deletes` (default 500) accounts match, it deletes nothing and logs an aborted run. Every run is a row in `private.purge_runs` (`ran_at`, `rule_a_count`, `rule_b_count`, `aborted`): check it with `select * from private.purge_runs order by id desc limit 7;`, and the schedule with `select jobname, schedule, command from cron.job;`. The foreign keys do the rest, as for Delete account: profiles, quotes and the social rows go, reports stay with the ids set to null, and the username is retired. A second pg_cron job, `purge-message-tombstones` (daily at 03:41 UTC), deletes copies of unsent messages older than 30 days, and a third, `purge-quote-tombstones` (daily at 03:43 UTC), deletes quote Undo tombstones older than a day. Rows are locked `FOR UPDATE SKIP LOCKED`, so an account being touched or creating its profile at that moment waits for the next run. Set `purge_exempt = true` (SQL editor) for anonymous accounts that must stay, such as the App Review helper. The migration schedules the job only where pg_cron is available (it is on hosted and on the local stack); elsewhere it applies with a warning. This is the one rule that tells anonymous accounts apart; access stays identical (pgTAP 10 and 12).
- Support: an anonymous account has no email, so nothing shows who owns it. Support must not delete an anonymous account on an emailed username alone; the owner deletes it in Account > Delete account.

## 8. Trade-offs (explicit)
| Decision | Chosen | Alternative | Why |
|---|---|---|---|
| Reminders | Local notifications | APNs and a cron sender | $0, no server, works offline. The cost is no cross-device sync and the 64-pending cap. |
| Rich text storage | Plain `body` plus UTF-16 runs | Markdown or HTML | Lossless for B/I/U, trivially searchable and pushable, safe to render. |
| Search | Client-side plus a Google link-out | FTS RPC or a quote API | Instant, offline, no vendor or cost. Revisit past about 5k quotes per user. |
| Posted and sent content | Server-built snapshot | A reference to the sender's row | Simpler RLS, stable for the recipient, and a report copies what friends saw. Costs a little duplicate storage. |
| Editor | UITextView representable | iOS 26 rich `TextEditor` | Mature attribute APIs (font traits, underline) and precise toolbar toggling. Revisit as SwiftUI matures. |
| Accounts | An anonymous Supabase account per iPhone | Email sign-in, a local-only app, one shared demo account | No email setup blocks testing, and RLS, friends and sharing stay as they are. The costs: no recovery after a reinstall, no sign-out, and weaker bans (docs/decisions/2026-10-20-anonymous-accounts.md). |
| Account delete | Edge Function with admin API | SECURITY DEFINER SQL deleting `auth.users` | The documented, supported path. Keeps the service role off the database API surface. |

   6. **"Confirm email" (only when email sign-in returns):** decide under Authentication → Sign In / Providers → Email. Recommended on for release, only once 2–5 work. You may turn it off for quick MVP testing. Then test sign-up and "Forgot password?" end to end with an address that is not on your Supabase team, opening each link within 5 minutes of requesting it (section 4, PKCE window).
   7. **App Review helper account:** there is no login, so App Review needs no demo account; the reviewer gets a fresh account on first launch. Report and Block need another person, so keep a helper account: install the TestFlight build on an iPhone you keep and leave it on Choose a username. `quotedhelper` is reserved, so give it to that account in the SQL editor: find the new anonymous user under Authentication → Users (newest first) and run `insert into public.profiles (id, username, purge_exempt) values ('<user id>', 'quotedhelper', true);` (`purge_exempt` keeps the purge away from it, section 7). Reopen the app, add a few quotes and leave it installed (deleting it loses the account). The reviewer adds that username from Friends; the pending request then offers Report and Block. Put the username in the review notes (`docs/app-store-submission.md` §8). Nothing secret goes in App Store Connect or the repo.
   8. **Daily report check:** see section 7 (Moderation). Optionally add the Database Webhook alert described there.
   9. **Security Advisor:** Advisors → Security Advisor. Once anonymous sign-ins are on, it lists the INFO entry "Anonymous sign-ins enabled" (`0012_auth_allow_anonymous_sign_ins`). That entry is expected and accepted: the policies deliberately don't check `is_anonymous`, and `supabase/tests/database/10_anonymous_user.test.sql` proves the parity (section 3). Don't add `is_anonymous` checks or turn anonymous sign-ins off to clear it. Fix any other finding.
   10. **Publishable key:** Settings → API Keys. If it changed, copy it into `Config/Hosted.xcconfig` (`SUPABASE_PUBLISHABLE_KEY`). Never put a secret key in the app.
3. **Support address:** `SUPPORT_EMAIL` is set in `Config/Shared.xcconfig`; override it in `Config/Release.xcconfig` only to ship a different address in the App Store build (Info.plist `SupportEmail`: Account → Contact support and the contact line of the bundled Privacy Policy, Terms and Guidelines). The `Check release settings` build phase fails any Release build or archive while it is empty, or while a legal page still has a draft banner.
4. **Legal pages:** have `App/Resources/Legal/*.md` reviewed, then publish the Privacy Policy and a support page at public URLs (for example GitHub Pages) for App Store Connect.
5. **Xcode:** choose your Team under Signing for both targets. If the bundle ID prefix `com.hwei` is taken, change it, along with the App Group `group.com.hwei.quoted`. Then Product → Archive → Distribute to App Store Connect, TestFlight first.
